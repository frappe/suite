# Use queued self-hosted batch transcription

Meet needs a saved Transcript after the conversation, so capture audio and queue it for batch transcription on infrastructure we control. Use a shared multi-site queue and worker pool whose capacity can be sized independently of the live-caption service, rather than preserving live-caption output as the authoritative Transcript. This accepts delayed results and temporary audio storage in exchange for queued processing and independent inference deployment. Third-party transcription services are excluded. Target delivery within one hour after capture ends as an internal operating target; delete source audio after the usable complete or partial Transcript is delivered and retain failed jobs' audio for at most seven days for retries. Size worker hardware from measured throughput and queue demand; validate recognition accuracy against checked references. See [the processing contract](../../../../specs/meet/002-batch-transcription.md) for the product boundaries.

Completion retries can return the existing Transcript only to the same worker and lease. A complete empty Transcript requires successfully processed audio with no speech. Missing or failed sources cannot establish silence. Transcription maintenance logs omit participant content and exception response bodies, since those bodies can contain source tokens.

The site locks the job and rechecks its status when claiming work. The shared worker pool coordinates scheduling across sites. The site persists recovery state separately from notification and source cleanup so either downstream service can be unavailable without losing recovery.

Checkpoints belong to one recognizer configuration and must not be reused after a model change. A failed source does not stop the worker from processing later speakers. Exact digital silence can bypass inference, while quiet audio still reaches the model.
