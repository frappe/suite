# Convex client guarantees and the Suite boundary

Research checked Convex's official documentation and `convex-js` source on 2026-10-06. This note describes Convex's behavior and Suite's present code. It does not select a Suite client policy.

## Client conventions Suite can adopt

- **Typed references and operation kinds.** Convex's generated `api` exports function references. A reference carries a query, mutation, or action kind and argument and return types. Client methods constrain the reference kind, so `query` cannot accept a mutation reference. These types come from generation, not the database protocol. Suite can generate equivalent metadata and types from its own contract. [Convex function reference API](https://docs.convex.dev/api/modules/server), [Convex client API](https://docs.convex.dev/api/classes/browser.ConvexClient), [Suite generator](../../../frontend/scripts/generate-contract.mjs), [Suite transport](../../../frontend/src/platform/transport/index.ts).
- **Two read forms.** Convex `useQuery` subscribes to a function plus arguments and updates as its database dependencies change. `ConvexClient.query` returns one result. Its [source](https://github.com/get-convex/convex-js/blob/main/src/browser/simple_client.ts) first checks `localQueryResult`; if absent, it creates a subscription, resolves or rejects on its first result, then unsubscribes. Thus a one-shot call can reuse a result already in the reactive client's memory. `ConvexHttpClient.query` is a separate, stateless HTTP call. Suite can expose both reactive and imperative reads, with explicit cache reuse rules. [Convex React](https://docs.convex.dev/client/react/overview), [JavaScript clients](https://docs.convex.dev/client/javascript/overview), [ConvexClient source](https://github.com/get-convex/convex-js/blob/main/src/browser/simple_client.ts).
- **Mutation result and error shape.** Convex mutation calls return a promise of the server result; a mutation error rejects it. The default `useQuery` throws server errors into React error boundaries, while the experimental result hook exposes pending, success, and error states. Convex application errors can carry structured `data`. Suite can choose these caller conventions without acquiring Convex's delivery guarantees. [Convex React](https://docs.convex.dev/client/react/overview), [error handling](https://docs.convex.dev/functions/error-handling/), [application errors](https://docs.convex.dev/functions/error-handling/application-errors).
- **Optional optimistic updates.** Convex attaches an optimistic function to a mutation. It edits loaded local query results, reruns if those results change, and rolls back when the mutation completes. It is an optional client behavior, not a required part of a typed reference. Suite already has optional optimistic entity patches and rollback, with different cache scope. [Convex optimistic updates](https://docs.convex.dev/client/react/optimistic-updates), [Suite server state](../../../frontend/src/platform/server-state/index.ts).
- **Actions.** Convex gives actions a separate reference kind and an async client call. Actions may use third-party APIs, run outside a single database transaction, and have no automatic retries or optimistic updates. A Suite action-like kind could distinguish side-effecting work from ordinary reads and writes, but its semantics need a Suite definition. [Convex React](https://docs.convex.dev/client/react/overview), [actions](https://docs.convex.dev/functions/actions).

## Guarantees a client facade does not create

- **Automatic freshness and consistent views.** Convex tracks each query's database reads and reruns it when relevant data changes. A query reads one logical database timestamp. The reactive client presents related query updates from one database state together. A shared cache or realtime notification alone does not supply those guarantees. Convex's stateless HTTP queries do not even guarantee a common snapshot across two calls. [Convex overview](https://docs.convex.dev/understanding/overview), [queries](https://docs.convex.dev/functions/query-functions), [React consistency](https://docs.convex.dev/client/react/overview), [HTTP rendering consistency](https://docs.convex.dev/client/nextjs/app-router/server-rendering).
- **Retrying a write without duplicate execution.** Convex React retries an outstanding mutation after connection loss until the backend confirms it. Its backend deduplicates retries so each call executes once. Convex mutations also run as transactions, with automatic retries for internal errors and conflicts. Suite cannot infer whether an HTTP write committed after a lost response. Retrying it safely needs a server-side request identity and deduplication contract, or operation-specific idempotency. A client-only retry would risk duplicate side effects. [Convex React retries](https://docs.convex.dev/client/react/overview), [Convex overview](https://docs.convex.dev/understanding/overview), [error handling](https://docs.convex.dev/functions/error-handling/).

## Suite's present boundary

[Suite transport](../../../frontend/src/platform/transport/index.ts) accepts generated operations with HTTP method, path, schemas, and error names. The method does not declare query, mutation, or action kind. It throws `TransportError` for failed requests, retries GET network failures, 429s, and 5xx responses up to two times by default, and does not retry writes. Output validation runs only in development.

[Suite server state](../../../frontend/src/platform/server-state/index.ts) wraps operations in query, infinite, mutation, or upload descriptors. It shares query records by a descriptor key, joins in-flight reads, keeps fresh data for a configured stale period, and refetches through explicit invalidation, polling, focus, and realtime events. It does not track database read dependencies or coordinate query responses as one snapshot. Its mutation `run` resolves to `undefined` on an unhandled failure while storing the error and reporting it. Ordinary mutations are serialized in this client instance; uploads run beside them. These are present implementation facts, not proposed rules.

The research constrains the typed-reference, read-mode, cache, error, retry, optimism, and action decisions in the [Suite API client map](../MAP.md). Human choices remain: which operations get each kind; whether an imperative read accepts cached data; how stale data and realtime invalidation work; whether mutation calls reject or return results; and which writes justify server idempotency. The sources do not establish that a successful Convex mutation promise alone means every subscribed UI has rendered its new value. Do not attach that promise to Suite without a separate contract.
