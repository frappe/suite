# Suite API client implementation plan

Status: complete. The [implementation report](implementation.md) records the operation inventory, removed adapters, retained protocols, and verification of the [specification](suite-api-client-spec.md). The [map](MAP.md) and [migration decision](tickets/008-migration-and-verification.md) record the approved direction. The prototype supplies caller examples, not runtime code. Each stage below names affected areas and a result a coding agent can verify. Proposed paths are marked **proposed**; inspect the checkout before fixing file names. Do not change stable operation IDs, URLs, permissions, or unrelated workflows.

## 0. Inventory and baseline

Record the starting revision, dirty files, active site, and each production caller. Cover generated Suite, Drive, and Mail references; `query`, `infinite`, `mutation`, and `upload` descriptors; direct `transport.request`; `createResource`, `frappe.call`, and raw fetch calls; editor sessions; owner workflows; and byte or collaboration protocols. For every operation, record owner, stable ID, proposed public name, declared kind, consumers, effects or justified `none`, scope, error handling, and removal condition. Recheck `frontend/src/platform/transport/generated.ts`, `frontend/src/apps/{drive,mail}/client/generated.ts`, `frontend/src/apps/drive/client/{nodes,operation,links,uploads}.ts`, `frontend/src/apps/mail/client/inboxSummary.ts`, and actual legacy callers. Treat this inventory as a migration checklist, not a new design questionnaire.

Capture present contract, import, type, bundle, and behavioral checks. Run no migration against a shared production site. Identify a configured test site for real permission, share-link, upload, and editor flows. Preserve unrelated checkout edits. The Suite architecture owner owns engine and generator work; product owners own policy and caller migration. Review a public interface change with the provider and an affected consumer owner as [the architecture charter](../../ARCHITECTURE.md) requires.

## 1. Generate complete references

Existing route tables: `suite/api/routes.py`, `suite/drive/http/translator.py`, and `suite/mail/http/routes.py`.

Depends on stage 0. Extend `suite/composition/http.py` route metadata with an explicit kind and public name for each generated operation. A union-body route can declare names for its variants, such as node patch rename, move, and trash. Export these in `suite/composition/contract.py`, which already expands union bodies into separate operation IDs. Update the applicable owner route tables, including Suite and Drive, only to declare these facts. Keep existing operation IDs and paths. Update `frontend/scripts/generate-contract.mjs` and the `Operation` type in `frontend/src/platform/transport/index.ts` to generate typed query or mutation references, public catalog paths, server page and byte facts, and validators. Allow one owner registration to supply paging behavior not expressed by the backend contract. Keep owner `contract.json` and `generated.ts` beside the present contracts. Reject duplicate public paths, missing kinds, invalid declared page metadata, and query/mutation mismatches. A generated reference must remain typed even when a validator loads lazily.

Acceptance: the backend exporter reproduces committed JSON; `yarn check:contract` reproduces generated TypeScript; compile-time examples accept valid Suite people, Mail inbox, and Drive node calls and reject wrong kinds or arguments. Run the contract drift checks in `.github/workflows/suite-ci.yml`; commit Python route declarations, JSON, and generated TypeScript together. Do not infer kind from method or rename HTTP endpoints to suit TypeScript.

## 2. Build one engine and prove three owners

Depends on stage 1. Adapt `frontend/src/platform/server-state/index.ts` and `frontend/src/platform/transport/index.ts` behind one product-neutral engine. Add the public `frontend/src/api/index.ts` (**proposed**) and a composition registration in `frontend/src/composition/api.ts` (**proposed**). Add lightweight owner API entries in `frontend/src/apps/{drive,mail}/client/api.ts` and a Suite owner entry near the current platform contract (**proposed paths**). Make the import boundary explicit in `frontend/scripts/check-import-boundaries.mjs`; do not add an exception baseline. Keep policies and validators lazy without importing product UI or private editor state into the startup graph.

Use one cache and one in-flight map for both caller forms. Partition query records, normalized entities, and IndexedDB persistence by session and effective access scope. Never put credentials in keys. Detach a canceled consumer without aborting a shared fetch that still has another consumer. Guard late replies by request generation and current partition. Keep the current call-order queue for ordinary mutations while uploads may run alongside. Roll back only the canceled or refused attempt's optimism. A canceled awaited call rejects with `AbortError`, clears pending, and records no refusal error or toast; it cannot imply a sent server write was undone. Apply final request outcomes once after transport retries, and never after abort. If challenge handling does not produce success, reject with the original refusal. Keep safe read retry behavior and no automatic write retry. Temporary descriptor adapters must call this same engine, with no second cache or toast path.

Register real policies and run thin vertical flows first: Suite account and people, Mail inbox summary, Drive node detail and rename. Verify a Vue caller, an outside-component `client` caller, disabled inputs and no-op disabled refetch, default fresh imperative reads, explicit `cache: 'prefer'`, rejection with reactive mutation error, detail/list reconciliation, and final feedback. A real Drive named-node and covered-node scope check must accompany rename. Do not use the prototype's fixture `none` policies for visit or settings.

## 3. Convert generated Suite, Drive, and Mail calls

Depends on stage 2. Move coherent caller groups to `@/api` references. Start with Suite account, site settings, invitations, and people. Cover Mail inbox and other generated Mail operations. Convert Drive details, lists, grants, shares, visits, settings, notifications, and access changes using owner policies under `frontend/src/apps/drive/client/`. Keep `frontend/src/apps/drive/client/links.ts` behavior for link selection, generation snapshots, sent tickets, challenges, and final outcomes. Convert editor Drive calls and outside-component sessions without importing product internals through the catalog.

Every migrated awaited mutation must handle rejection. Remove checks that treat `undefined` as a failed result; confirm success UI follows only success. Declare effects or explicit `none` for every generated mutation and add a CI coverage check. Verify Recent after visit, settings readers after settings writes, lists after rename/move, and access data after link changes. Add broad scenario tests through `@/api` with a fake network boundary, plus representative browser flows on the configured site. Test overlapping writes, stale query replies, scope changes, observer disposal, shared cancellation, read retry, realtime, and permission refusals. Do not copy policy arrays into tests as the expected behavior.

## 4. Paging, uploads, bytes, and composite work

Depends on the applicable owner conversion in stage 3. Add `useInfiniteQuery` for query references with page capability. Put cursor or offset metadata in contract facts or one owner policy. Check reactive arguments, disabled state, page exhaustion, argument changes, stale pages, `hasNext`, `isFetchingNext`, and list effects. Add `useUpload` for typed owner transfer references around the current Drive upload protocol in `frontend/src/apps/drive/client/uploads.ts` and upload feature area. Check its typed file and resume inputs, `isPending`, `progress`, `error`, and `cancel()`. Keep create, chunk or direct upload, probe/resume, finish, progress, cancel, scope, and failure cleanup together. Expose raw-byte downloads explicitly without entity normalization.

Keep Writer, Sheets, and Slides document sessions and Drive creation as named product workflows. Inventory and convert their ordinary generated calls while preserving their collaboration transports and partial-success cleanup. Do the same for Mail import or attachment flows where they use multi-request protocols. Verify a real upload and resume on a test site, a canceled transfer, a refusal, a byte download, and editor open/save flows. Do not claim these from mock progress. Yjs, WebRTC, and long-lived streams remain explicit protocol exceptions.

## 5. Contract and convert remaining legacy calls

Depends on stages 1–4 for shared behavior. Add route contracts for ordinary legacy product APIs before migrating callers. Declare kind and public name for each generated operation, including union-body variants, and owner policies for each mutation. Convert legacy `createResource`, `frappe.call`, and direct request users in product-owned groups. Preserve named composite workflows where an endpoint sequence has real business meaning. Fix rejecting-error handling in the same group. If an endpoint cannot yet be contracted, keep one inventory row with its owner, protocol or backend blocker, exact consumers, and removal gate. Do not add new ordinary callers to it.

At each group boundary, remove the now-unused old descriptor factory, `driveOperation` wrapper use, and non-throwing adapter. Direct `transport.request` remains internal to transport, byte or protocol implementations, and inventoried uncontracted legacy paths only. A temporary adapter shares the engine and feedback. Do not leave a permanent alternate ordinary request API.

## 6. Remove adapters and close the migration

Depends on the converted caller inventory. Remove the old query/mutation/infinite/upload builder exports when production imports reach zero and replacement behavior checks pass. Remove the named non-throwing adapter only after all consumers handle rejected writes. Remove caller-level Drive scope wrappers only after named, covered, challenge, and access-change checks pass. Remove `createResource` dependencies when contracted consumers reach zero. Prove that no ordinary caller constructs a transport request, descriptor, or policy wrapper.

Update `STANDARDS.md`, `ARCHITECTURE.md`, `frontend/AGENTS.md`, and affected composition guidance in the same implementation changes. Mark the older [server-state guideline](../unified-frontend/references/server-state-client.md) superseded and link this spec; keep its history. Update import and architecture rules, examples, and exact debt baselines as old paths disappear. Never grow a baseline for this migration.

Run relevant backend behavior tests and the backend JSON drift check. In `frontend/`, run focused tests, `yarn format`, `yarn lint`, `yarn check:untranslated`, `yarn typecheck`, `yarn check:contract`, `yarn check:import-boundaries`, `yarn check:bundle-budget`, and `yarn build`. Inspect the initial import graph for product UI and validator cost; meet the existing bundle budget without raising it. Use real browser flows for permission, Drive share-link scope and refusal, paging, transfer, and editor protocols. Record the checkout revision, converted consumers, removed adapters, generated-file changes, exact check results, and remaining protocol or legacy exceptions with owners and removal conditions. Migration is complete when ordinary callers need only a generated reference and a client or composable call, and every temporary adapter has been removed.
