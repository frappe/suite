Frappe Suite · accepted architecture charter

One suite. Deep product modules.

A codebase structure for the Drive rewrite that gives each product a clear owner, keeps cross-product dependencies small, and turns architectural intent into enforceable rules.

Accepted for the Drive rewrite Modular monolith Backend + frontend Behavior spec unchanged
Architecture in one sentence: each Suite product owns a deep module, products collaborate only through explicit interfaces, and Suite composition wires those modules together.

Drive is foundational because several products use its tree, sharing, and storage model. It remains a product module—not suite_core, a shared utility collection, or a database wrapper.

suite_core may be used by every product but must not import product implementations. Suite composition may register every product because composition is where dependency directions meet.

The Drive seam

The suite.drive package root is the only supported Python interface outside Drive. Its names live in suite/drive/__init__.py and expose complete outcomes needed by real production callers.

Allowed · request an outcome
from suite import drive

node = drive.create_document(
    content_type="writer",
    parent=parent,
    title=title,
)

drive.touch(
    "Writer Document", docname
)
Forbidden · assemble internals
from suite.drive._core.quota import admit
from suite.drive._core.nodes import insert_node
from suite.drive.doctype.drive_node \
    import DriveNode

admit(root, size)
insert_node(values)

Public workflow set

  • check access
  • create/copy document or file
  • touch and take version
  • manage recording reservations
  • Content Type declarations
  • documented roles, results, and errors

Private implementation

  • quota admission counters
  • activity row writes
  • grant predicates
  • preview rendering jobs
  • DocType queries/controllers
  • blob keys and driver details

The final export list comes from the production caller inventory. An internal test is not a reason to publish an operation.

Meta codebase rules

01

Ownership & placement

  • Product behavior MUST live under the product that owns its language.
  • suite_core MUST remain product-neutral.
  • Cross-product orchestration MUST live in composition.
  • Product adapters live with, and are owned by, that product.
02

Dependency direction

  • Products MUST NOT import another product's implementation.
  • Cross-product calls use the provider's declared interface.
  • New dependency cycles are forbidden.
  • Hook strings and dynamic imports obey the same rules.
03

Interfaces & depth

  • Each module has one intentional interface.
  • Interfaces expose workflows, not database primitives.
  • Every new public operation has a real caller.
  • Errors, ordering, permissions, and performance are part of the interface.
04

Seams & adapters

  • Add a seam only when behavior genuinely varies.
  • A seam should have at least two justified adapters.
  • HTTP and WebDAV translate; they do not own Drive policy.
  • Tests do not turn an internal seam into a public one.
05

State & invariants

  • Every fact has one source of truth.
  • Drive owns title, place, grants, lifecycle, versions, comments, and usage.
  • Content products own bodies and editor live state.
  • Mutations leave all related records consistent or use a documented resumable process.
06

Shared code

  • Code stays in its product until two real consumers need it.
  • Shared code uses neutral language and has an owner.
  • utils, common, and shared are not ownership-free zones.
  • Keep duplication when domain rules differ.
07

Testing

  • The interface is the primary test surface.
  • Tests assert observable outcomes and invariants.
  • Adapter tests cover translation and protocol behavior.
  • Replace shallow legacy tests; do not layer both forever.
08

Frontend modules

  • Each apps/<product> owns its UI and client state.
  • Products do not import another product's pages, state, or internals.
  • Cross-product use goes through a lightweight declared interface.
  • Code enters platform only with neutral language and multiple consumers.
09

Review & stewardship

  • Product owners own product implementation.
  • Suite architecture owns composition, core, shell, and enforcement.
  • Interface changes need provider and consumer review.
  • Data ownership changes update the context map first.
10

Migration discipline

  • New code follows the target structure; untouched code may remain.
  • Existing debt is baselined and may only shrink.
  • Build is additive; Cleanup waits for its explicit gates.
  • Behavior remains sourced from the Drive layer spec.

Make the rules fail in CI

GATE 1
Python importsAST check blocks product internals, Drive private modules, cycles, and product imports from suite_core.
GATE 2
Frontend importsBlock @/apps/other/… except declared package interfaces such as @/apps/drive.
GATE 3
Public exportsSnapshot suite.drive.__all__ so accidental exports fail review.
GATE 4
Adapter contractsEvery registered Content Type adapter runs through one shared behavior suite.

Begin with an explicit allowlist of existing debt. New violations fail immediately; allowlist entries disappear as products migrate.

Change review checklist

  1. Which product owns this behavior and vocabulary?
  2. Where does the module's interface live?
  3. Does the caller request an outcome or assemble steps?
  4. Which invariants does the implementation hide?
  5. Does this add a dependency edge or cycle?
  6. Which two adapters justify a new seam?
  7. Can tests use the caller-facing interface?
  8. Does shared code have multiple consumers and an owner?
  9. Must the context map record a data ownership change?
  10. Can CI enforce the architectural decision?

Adoption before and through Drive

Before Stage 1
Freeze the rules

Accept the charter, inventory Drive callers, decide package exports, and add import checks with a debt baseline.

Drive rewrite
Build behind the seam

Implement the new Drive workflows. HTTP and WebDAV adapt into them. Preserve the behavior spec.

Product adoption
Move one adapter at a time

Writer, Sheets, Slides, Meet, and Mail stop importing Drive internals as their paths migrate.

Frontend adoption
Use the generic Drive route

Drive UI stops calling Writer and Sheets creation endpoints directly. Cross-app clients use declared package interfaces.

Cleanup release
Delete the old surfaces

Remove shims, File overrides, legacy modules, and their shallow tests only after migration gates hold.

Next contexts
Apply the pattern selectively

Map Mail and Calendar next, especially their existing dependency cycle. Do not force a mass rewrite.

Accepted decision
The suite.drive package root is the only supported cross-product Python interface. Use from suite import drive, keep implementation modules private, and enforce the boundary before Drive Stage 1.

This changes the code shape without reopening the Drive behavior model. It gives the rewrite a durable seam that later Suite products can follow.
