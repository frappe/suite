    Suite · Drive layer · Decision 014

    The front door

    Nine decisions are closed. They describe tables, roles, quota, and links. None of them says how a browser asks for any of it. The architecture doc has no HTTP section at all. This page shows what is there today, what the closed decisions already fix, and the choices left.

    9 of 14 decided · Counted from the code on 4 September 2026

    What is there today

    Drive has 69 whitelisted methods in 11 files. 26 of them accept guests. There is no route table: every call is /api/method/suite.drive.api.<module>.<function>, which is Frappe's normal way of doing things.

    Reads

    Five list endpoints, all funnelling into one get_query_data. Offset paging. Seven sortable fields. Page size 50 from the client, capped at 100.

    Writes

    One verb per action: rename, move, remove_or_restore, delete_entities, set_favourite, update_access.

    Bytes

    Four separate paths: get_file_content, stream_file_content, get_thumbnail, and a three-step zip download (start, poll, fetch).

    Four things cannot simply be renamed.

    • api.s3.fetch?path= is written into File.file_url rows in live databases. A patch already exists for one earlier rename of it.
    • overrides.file.get_file_for_doc is the cross-app SDK. Writer, Sheets, and Slides call it through a built bundle checked in at suite/public/frontend/assets/sdk-o7hlQ1xj.js.
    • api.files.track_visit and api.files.upload_file are called from Writer, Sheets, and Slides, not just Drive.
    • /dav is bound by Finder and Windows Explorer.

    What the closed decisions already fix

    Five closed tickets handed this one a list of requirements. These are inputs. They are not up for discussion here.

    FromWhat it demands of the API
    Publishing Publish is a grant to $PUBLIC, not a verb. The grant endpoint refuses $PUBLIC above READ, and on a root.
    Link sharing A link is a grant with principal $LINK. Add rotate and unlock. Every endpoint reads X-Drive-Links. A password link with no ticket returns a distinct locked answer, not a 403.
    WebDAV Create and replace take a client modification time. Activity gains a client column. One copy endpoint, and it is the COPY primitive.
    Quota A usage endpoint per root. Admin endpoints to set quota and purge an archived root. Over quota is its own error, never a permission error.
    Migration Favourites, recents, activity, and notifications read the four reshaped tables. Notification is a pointer to an activity row.

    The frame

    Everything below sits in one picture. There is a Python SDK, an HTTP layer, and a WebDAV layer. Two of the three already exist as decisions. The middle one is what this ticket writes.

    The ten entry points. create, update, open, browse · share, role_of, readable_sql · the content registry, the mixin, node_of. update() alone covers rename, move, trash, restore, and byte replacement.

    Question 1 — RPC or routes? answered

    Answer · 4 September 2026

    Real routes, under a suite namespace. Not /api/method/suite.drive.api.node.update. Something a person can read:

    PATCH /api/suite/drive/nodes/<id>

    Second half of the answer: harden the site by denying the framework's default API surface on the suite frontend, and keeping it for Desk system users — the shape Frappe Cloud's Press already uses.

    What that costs, in facts

    FactConsequence
    /api/suite/… matches no existing rule (api/v1.py:152, api/v2.py:604) The namespace is free. Nothing to reserve or rename.
    API_URL_MAP is built at import time (api/__init__.py:95) An app cannot add a route. The request has to be caught before the map is consulted.
    before_request runs inside init_request() (app.py:226), ahead of the /api/ branch (app.py:134) That is the catch point. Drive already uses it for /dav, returning its response by raising an HTTPException (app.py:150).
    validate_auth() runs after it (app.py:118) At catch time the session cookie is resolved, but Authorization: token key:secret is not. WebDAV pays this today by doing its own Basic auth.

    The hardening is already half-written. suite/hooks.py:403-452 declares ALLOWED_PATHS, ALLOWED_WILDCARD_PATHS, and DENIED_WILDCARD_PATHS = ["/api/"] — deny everything under /api/, then allow back /api/method/suite.*.api., login, ping, upload, OAuth, realtime, and /dav. Nothing in suite or frappe reads those lists. The gate is external, so on a self-hosted bench nothing is denied today.

    Question 1b — one namespace, or one per app? answered

    Suite is eight apps sharing a site: Drive, Writer, Sheets, Slides, Mail, Calendar, Meet, and the product shell. /api/suite/nodes/ reads beautifully — and it spends the whole namespace on Drive's noun.

    Answer · 4 September 2026

    An app segment. /api/suite/drive/…. One segment buys collision-free nouns across eight apps, a readable owner when a route breaks, and one allowlist prefix per app instead of one per route.

    A · Flat suite namespace
    /api/suite/nodes/<id>
/api/suite/grants/<id>
/api/suite/messages/<id>   mail
/api/suite/events/<id>     calendar

    For: shortest URLs. One resource list for the whole product, which is what the product claims to be.
    Against: eight apps must agree on every noun forever. Drive and Mail both want attachments. Nothing tells you which app owns a route when it breaks.

    B · App segment chosen
    /api/suite/drive/nodes/<id>
/api/suite/drive/roots/<id>
/api/suite/mail/messages/<id>
/api/suite/calendar/events/<id>

    For: one segment buys collision-free nouns, a readable owner, and an allowlist entry per app (/api/suite/drive/) instead of per route.
    Against: one more segment. That is the whole cost.

    Question 1c — how do the routes get mounted? answered

    Three ways to make PATCH /api/suite/drive/nodes/abc reach Python. They differ in how much of Frappe's request machinery Drive keeps.

    Answer · 4 September 2026

    Translate, then delegate. The pretty path is the public contract. A before_request translator matches it, seeds frappe.form_dict from the path segments, rewrites PATH_INFO, and lets the framework do the rest.

    PATCH /api/suite/drive/nodes/abc   { "title": "Q3" }
      ↓ translator
PATH_INFO  → /api/v2/method/suite.drive.api.node.update
form_dict  → { node: "abc", title: "Q3" }
      ↓ frappe: auth, CSRF, rate limit, response
{ "message": { … } }              envelope unchanged

    Frontend
    out of scope, but someone pays    		 Nearly nothing. frappeRequest.ts:66 already passes any url starting with / through untouched, and :83 already honours options.method. So createResource({url: '/api/suite/drive/nodes/x', method: 'PATCH'}) works today.

    Unchanged WebDAV, the Python SDK, and the shim story for the old 69 methods. Same work either way.

    Question 2 — how many routes? answered

    The SDK has ten entry points; update() alone covers rename, move, trash, restore, and byte replacement. Today's API has 69 methods. With routes chosen, the question becomes: does a node change through one PATCH with fields, or through a route per verb?

    Answer · 4 September 2026

    One PATCH for what can be undone. DELETE for what cannot.

    PATCH  /api/suite/drive/nodes/<id>
         { "title":  "Q3 deck"  }      rename
         { "parent": "folder-9" }      move
         { "state":  "trashed"  }      trash
         { "state":  "active"   }      restore

DELETE /api/suite/drive/nodes/<id>    purge — terminal

    DAV MOVE keeps one path, because a MOVE is a rename, a move, or both, and it does not know which.

    One thing pulls toward the PATCH. The architecture doc says update() "gives WebDAV MOVE, the UI, and content sync one tested path". A DAV MOVE is a rename, a move, or both, and it does not know which — so it wants one route that takes both fields.

    A · One PATCH, all of it
    PATCH /nodes/<id>
  { title }
  { parent }
  { state: "trashed" }
  { state: "active" }
  { state: "purged" }

    Mirrors the SDK exactly. One route to authorize and test.
    Against: an accidental state: "purged" is unrecoverable, and it looks like every other field.

    B · A route per verb
    PATCH /nodes/<id>   title
POST  /nodes/<id>/move
POST  /nodes/<id>/trash
POST  /nodes/<id>/restore
POST  /nodes/<id>/purge

    Each route validates only its own arguments, and gets its own rate limit and activity verb.
    Against: five routes that must stay in step, and DAV MOVE has to pick one.

    C · PATCH, but purge is DELETE chosen
    PATCH  /nodes/<id>
  { title }
  { parent }
  { state: "trashed"
        | "active" }

DELETE /nodes/<id>   purge

    Reversible changes are one PATCH, so DAV MOVE still has one path. The one irreversible act is the one HTTP verb that means it.

    Question 3 — who checks permission? answered

    The architecture doc says Drive "owns its endpoints and preflights itself". That was written about the framework seam, not about this one. So it is still open whether the check lives in the endpoint or below it.

    Answer · 4 September 2026

    The SDK checks. The HTTP layer translates. A route handler parses the path, seeds principals from X-Drive-Links, calls the SDK, and maps the exception. Three callers reach the same nodes — routes, /dav, and other suite apps — and all three get one rule because none of them owns it.

    A · SDK checks, HTTP translates chosen
    def patch_node(node, **fields):
    return drive.node.update(
        node, **fields)
    # raises. that is all.

    One home for the rule. WebDAV, the HTTP layer, and Sheets cannot disagree, because none of them decides.

    B · Endpoint checks first
    def patch_node(node, **fields):
    require(node, EDIT)
    return drive.node.update(
        node, **fields)

    Lets the endpoint fail early and give a better message. Costs a second read of the grants, and a second place the rule can be wrong.

    Question 4 — what does an error look like? answered

    Today the same condition is signalled two ways. files.py:73 throws; files.py:290 raises. One endpoint hand-builds a v2-shaped error body so the SPA routes correctly (permissions.py:124). Search swallows every exception and returns {"error": …} with a 200.

    Answer · 4 September 2026

    The v2 errors[] shape. The exception class name is the code; http_status_code on the class gives the status.

    class DriveOverQuota(frappe.ValidationError):
    http_status_code = 413

HTTP 413
{ "errors": [ { "type": "DriveOverQuota",
              "message": "Needs 4 MB, 1 MB free" } ] }

    What today is a hack at permissions.py:124 becomes the rule. Success rides the same envelope: { "data": … }.

    No upstream ask. useCall already speaks this. frappe-ui's newer data-fetching layer parses the v2 errors[] array natively (data-fetching/useFrappeFetch.ts:90-105), surfacing type, message, title and exception as a FrappeResponseError. It is the older createResource path (frappeRequest.ts:118) that reads exc_type, and Drive is leaving it.

    ClientFits Drive's routes?
    useCall Yes. Takes an arbitrary url (useCall.ts:54) and GET | POST | PUT | DELETE (useCall/types.ts:11). Unwraps data.data, which is what frappe/api/__init__.py:66 writes.
    useList
    useDoc    		 No. Both build /api/v2/document/<doctype> URLs (useList.ts:65, useDoc.ts:63) — the framework's generic document API, which bypasses the grant engine.
    createResource The v1 path Drive uses today. Superseded here.

    Both envelopes must be v2, together. useCall reads success as { data: … } and failure as { errors: [ … ] }. Translating to /api/v2/method/… produces both. Translating to /api/method/… produces neither.

    Question 5 — how does paging work? answered

    Today's paging has a wart worth understanding. The SQL window is taken first, then rows the user cannot see are dropped. So a page of 50 can return 12 rows, and the next offset is not start + limit — it is a raw offset the server computes and hands back (list.py:477-495).

    The new engine has the same shape: fetch child ids, then batch-read grants over that page. Filtering still happens after the window.

    Answer · 4 September 2026

    An opaque cursor. The client echoes back a string it never parses.

    GET /api/suite/drive/nodes/<id>/children?limit=50

{ "data": { "rows": [ … 12 rows … ],
            "next_cursor": "b2Zmc2V0OjUw" } }

GET …/children?limit=50&cursor=b2Zmc2V0OjUw

    It holds an offset today. It can hold a keyset later, with no call site changed. No page jumping — the honest answer while filtering happens after the window.

    A · Keep offsets

    start, limit, and a server-computed next_start. Honest about what it is. Clients can jump to page 40 — and will get wrong results when rows shift.

    B · Opaque cursor chosen

    {rows, next_cursor}, where the cursor is a string the client only ever echoes back. It holds an offset today and can hold a keyset later without a client change.

    C · Filter before the window

    Push the grant join into the list query so a page of 50 is 50 rows. Decision 004 froze the index that makes the unfiltered scan fast; a join would need re-benchmarking.

    Question 6 — what is in a node's JSON? answered

    get_entity_with_permissions returns the file, the access bits, the owner's name and avatar, the breadcrumb chain, the favourite flag, and a share count — in one call. The list endpoints return a thinner row. Two shapes for one thing.

    Answer · 4 September 2026

    One node shape, with opt-in expansions. A list row and a detail fetch carry identical base fields, so the client has one type.

    GET /nodes/abc
{ "data": { name, title, kind, parent, state, size, modified, owner } }

GET /nodes/abc?expand=access,breadcrumbs,preview
{ "data": { …base…, "access": {…}, "breadcrumbs": […], "preview": {…} } }

    Extras are named in the query, so a 50-row folder page pays for no breadcrumb chains it did not ask for.

    A · One node, opt-in extras chosen
    GET /nodes/<id>
  ?expand=access,
          breadcrumbs,
          preview

    The base node is always the same fields, in lists and in detail. Extras cost extra queries only when asked for. One serializer to keep correct.

    B · Purpose-built payloads
    GET /nodes/<id>/children
  row shape
GET /nodes/<id>
  page shape

    Each view returns exactly what it needs, no negotiation. That is today's design, and it is why the two shapes drifted apart.

    Question 7 — what happens when half a batch fails? answered

    Today move, delete_entities, remove_or_restore, and set_favourite all take lists. But PATCH /nodes/<id> is singular. Select 30 files, move them, and 3 have no EDIT grant.

    Answer · 4 September 2026

    A batch route that reports per item. Partial success is a result, not an error.

    POST /api/suite/drive/nodes/batch
{ "nodes": [ … 30 ids … ], "patch": { "parent": "folder-9" } }

{ "data": { "ok": [ … 27 ids … ],
            "failed": [ { "node": "c", "type": "DriveForbidden" } ] } }

    The 27 move. The UI names the 3 that did not. One gesture stays one request and produces 27 activity rows, not 30 requests.

    A · All or nothing

    One failure rolls the whole batch back and returns one error. Simple to reason about, and infuriating when one file in thirty is locked.

    B · Per-item results chosen
    {"ok": ["a","b"],
 "failed": [
   {"node":"c",
    "code":"forbidden"}]}

    The 27 move. The UI names the 3 that did not.

    C · One node per call

    The client loops. Honest, matches the SDK exactly, and turns a 30-file move into 30 round trips and 30 activity rows.

    Question 8 — what happens to the 69 methods? answered

    The frontend is out of scope for this map. But the frontend still has to work on the day the migration patch runs. Every one of these names is called by shipped JavaScript.

    Answer · 4 September 2026

    Shim, then drop. Old names become thin forwarders into the new SDK and die one release later — the same two-step shape decision 011 chose for the data.

    Build patch (additive)
  routes live
  suite.drive.api.files.rename  →  drive.node.update
  … × 69 forwarders

Cleanup patch (one release later)
  forwarders deleted, gated on the SPA having moved

    The API and the tables move on one schedule. The SPA rewrite does not have to land in the same release as the backend.

    A · Cut over

    New names only. The SPA is rewritten in the same release. Nothing to keep in step, and the two efforts must land together.

    B · Shim, then drop chosen

    Old names stay as thin forwarders that call the new API. They die in the Cleanup patch, one release later — the same two-step decision 011 already chose for the data.

    C · Keep them

    The old surface is the public API forever; the new one is internal. No migration, and 69 methods to keep correct against a model they no longer match.

    Three names may not get a choice. api.s3.fetch is inside stored data. get_file_for_doc is inside a checked-in built bundle. /dav is inside other people's file managers. Those are permanent whatever we decide here.
