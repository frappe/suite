Accepted · root identity and target fields

One root, two records with different responsibilities.

Grant.node    → a Drive Node
Activity.node → a Drive Node

Both records use the same id. The metadata has a required, unique Link to its root node.

Descendants point to the root node. The root node itself has no parent or root pointer. Root-relative paths exclude its id.

Offboarding

Archive the metadata. Keep the root node, descendants, and existing grants. No tree rewrite.

Quota admission

Update used bytes on the metadata row. The root node carries no copy of those counters.

Pair rules: create both records and anchor grants in one transaction. Root nodes cannot be moved, copied, or trashed.

Only the dedicated archived-root purge removes the pair after its descendants and references. Migration preserves existing root ids.

Verification: pairing, rollback, concurrent creation, ancestry, top-level listings, quota lookup, deletion order, and migration resumption.

Accepted · group roles

Positive grants add access. Explicit DENY wins a tie.

Groups at the same depth and tierResult
READ + EDITEDIT
READ + EDIT + DENYDENY

Nearer grants still take precedence. At equal depth, a direct user grant outranks group grants. Public/link resolution remains separate.

Accepted · removal and denial

Removing a grant does not silently create a deny.

Remove this grant

Delete the local row. Inherited access may remain. Show its source in the UI.

Deny access here

The user explicitly chooses DENY. Write role 0 through the normal grant operation.

Folder: Alex has READ
└─ File: Alex has EDIT

Remove the file grant → Alex inherits READ.
Explicitly deny Alex → Alex is denied at this file.

This distinction also applies to public access. Removing a local public grant can leave inherited public access.

Keep expired grants. No expiry cleanup.

Accepted · restore destination

The user chooses a replacement location.

Projects · Active
└─ Old work · Trashed
   └─ Notes · Trashed

Restore Notes
     ↓
Original parent unavailable
     ↓
Ask where to restore it
     ├─ Choose a valid destination → restore there
     └─ Cancel → keep Notes in Trash

Never move it to the nearest Active ancestor automatically. Do not automatically restore its parent folders.

If the original parent is available, ordinary restore keeps the original location. Alternate destinations stay within the same root.

Backend: require an explicit destination before mutation. Frontend: provide the picker. Test destination permissions, title conflicts, and subtree paths.

Accepted · link scope and limit

Send the links this operation needs.

A share link contains a code that identifies a sharing grant. The browser remembers each code with its target.

Open Sales deck       → Sales code
Open Product deck     → Product code
Load Company update   → Company + Sales + Product codes

The combined presentation needs separate access to its referenced decks. Being included in a presentation grants no access by itself.

  • Ordinary browsing uses the active share link, including its folder descendants.
  • Combined content includes the relevant additional codes.
  • Unrelated API calls do not carry the entire remembered token store.
  • Allow at most 20 supplied items per request. Reject excess with a clear HTTP 400 error.
  • Never silently discard extra codes. Large composites load in smaller groups.

Every group rechecks access to the composite and requested references. Relevant collaboration tokens follow the same limit.

Twenty is an initial bound, not a benchmark result. Specify client token scoping and grouped-load APIs together during ticketing.
