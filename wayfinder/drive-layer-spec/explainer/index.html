    The new Drive layer

    Drive is being rebuilt as one permissioned tree that every Suite product borrows. This page explains what changes, why, and how far the design has got.

    9 of 14 decisions closed · Design frozen 2 September 2026 · Branch forge/wayfinder-drive-layer

    The short version

    Every Suite product stores something. Writer stores documents, Slides stores decks, Sheets stores workbooks, Meet stores recordings, Mail stores attachments. Today each one solves storage and sharing again, in its own way. Sheets has its own share dialog. Slides has its own image endpoint. Drive has a third model that the others do not use.

    The new Drive layer gives all of them one answer. Drive holds the tree, the names, the permissions, and the lifecycle. A product holds only the body of its own document. One file, one place, one set of rules.

    One tree

    A new Drive Node table holds every file, folder, and document in the site. Each row carries the full path to its root.

    One permission table

    Drive Grant is the only place rights are stored. It is also the only place they are read from. No derived copies to keep in step.

    One contract

    A product declares how to create, copy, export, version, and purge its documents. Drive does the rest.

    Where the work stands

    The architecture was chosen on 2 September 2026 after a benchmark of three candidate designs. Since then the open questions have been worked one at a time, each closed with a written decision. Nine of fourteen are done.

    What Drive does today, and why it has to change

    Today a Drive file is a framework File row with five custom fields bolted on. Rights live in Drive Permission, which has five independent checkboxes: read, comment, share, upload, write, plus a deny flag. Rights are inherited from folders, so to answer "may Alice open this file?" Drive must walk from the file up to the root.

    It walks that path with a recursive SQL query. One query per file. A folder page of sixty rows runs sixty recursive queries.

    suite/drive/utils/__init__.py:455 · one of these per row
    WITH RECURSIVE generated_path as (
    SELECT `tabFile`.file_name, `tabFile`.name, `tabFile`.folder, 0 AS level
    FROM `tabFile` WHERE `tabFile`.name = %(entity_name)s
    UNION ALL
    SELECT t.file_name, t.name, t.folder, gp.level + 1
    FROM generated_path as gp JOIN `tabFile` as t ON t.name = gp.folder
)
SELECT gp.file_name, gp.name, gp.owner, p.user, p.deny, p.read, p.upload, p.write
FROM generated_path as gp
LEFT JOIN `tabDrive Permission` as p ON gp.name = p.entity AND {perm_filter}
ORDER BY gp.level DESC, {tier}, p.deny DESC;

    The four problems

    Lists under-report

    Plain SQL cannot express inherited rights, so list queries only find directly shared rows. The code says so: "impractical in SQL — left to has_permission". Counting children needs a bespoke double-EXISTS so that a folder of 512 migrated teams does not report all 512 to someone who can open three.

    Owner beats deny

    An owner short-circuit returns full access before any grant is read. It overrides an explicit deny. That contradicts the nearest-wins rule the rest of the engine follows.

    Every link is the same link

    The link principal is the empty string. It carries no token, no password, no expiry. It matches every link-shared node on the site.

    Sheets is somewhere else

    Sheets uses framework DocShare rows, not Drive permissions. Sharing a sheet in Drive grants nothing on the sheet, and the reverse is also true.

    Three designs were measured, not argued about

    Agents built three candidate engines and benchmarked them on 250k nodes and 30k grants: a flattened table with one derived row per node-principal pair, a closure table of every ancestor edge, and a path model that stores the ancestor list on the node itself and resolves rights in Python.

    Speed was not the deciding argument. Correctness under failure was. Agents red-teamed thirteen scenarios against each design. The flattened model failed three of them in ways a user would never see: derived rows that keep granting access after the grant is deleted, a restore-after-move that silently corrupts the paths and rights of a trashed subtree, and a 5,000-node WebDAV move that reports success before rights have converged. The path model has no derived state, so it cannot drift.

    The one number that changed the schema. Adding the index (parent, state, title) took the 10,000-child folder page from 11.7 ms to 0.57 ms, from 30,202 pages read to 3. It costs 5 MB per 250k nodes and 1.5% on insert. Frozen.

    The idea: put the path on the row

    Every Drive Node carries a path column. It is not a file path. It is the list of ancestor ids, slash-delimited, up to 40 deep.

    Three things fall out of that one column:

    Ancestors are free

    Splitting /r1/q3/s9/ gives every ancestor id. Zero queries.

    Move is one UPDATE

    WHERE path LIKE '/r1/q3/%' selects the whole subtree. 1,000 nodes in 9.5 ms.

    Nothing on disk matches

    Blobs are addressed by their content hash. A rename or a move touches no bytes at all.

    The permission engine, in fourteen lines

    A permission check parses the path, runs one query for the grants on that path, and composes the answer in Python.

    the whole read path
    def effective_role(node_path: str, principals: list[str]) -> int:
    ancestors = parse_ids(node_path)          # <= 40 ids, zero queries
    rows = frappe.db.sql("""
        SELECT node, principal, role FROM `tabDrive Grant`
        WHERE node IN %(ancestors)s AND principal IN %(principals)s
          AND (expires_on IS NULL OR expires_on > NOW())""", ...)
    # nearest wins: minimum depth, then principal specificity.
    # role = 0 is a stored value and means deny.
    return compose_nearest_wins(rows, ancestors, principals)

    Nearest wins. The grant closest to the node decides. A grant on the file beats a grant on its folder, which beats a grant on the root.

    Deny is level zero. A deny is not a flag and not a second table. It is an ordinary grant row whose role happens to be 0, so it competes on exactly the same rules. "Everyone except Bob" is one row.

    The last row matters more than the timings. The grant rows are the explanation, ordered by depth and specificity. An explain() call is trivial to write because there is nothing to reconstruct.

    Six roles, in a strict ladder

    Five independent checkboxes become one integer. Each level contains every level below it, so "upload but not read" is not a state the system can express. The gaps of ten leave room to insert a level later.

    The creator rule. UPLOAD is add-only, so someone who can add a file to a shared folder cannot edit it afterwards. To fix that without reintroducing owner rights, the engine writes one EDIT grant naming the creator on the node they just made, and only when their effective role is below EDIT. Rights stay grant rows and nothing else. Owning a file grants nothing.

    Five kinds of principal, one column

    A grant names a principal: a string in the principal column. There is no separate table for groups, for publishing, or for links. They are all rows in Drive Grant.

    PrincipalWho it meansCeiling
    alice@example.com One user. The most specific match. MANAGE
    $GROUP:<name> A user group. MANAGE
    $GENERAL Any signed-in user on the site. A fresh Shared Root carries this at UPLOAD. MANAGE
    $PUBLIC Anyone at all, signed in or not. Every session holds it, guests included. READ
    $LINK:<token> Whoever holds one secret. 22 characters of base62, about 128 bits. EDIT

    Publishing is not a feature. A published node is one row: (node, $PUBLIC, READ). Unpublishing deletes that row, or writes a $PUBLIC deny if READ still reaches down from a folder above. There is no published column, no second table, no publish verb in the audit log, only a grant write whose principal happens to be $PUBLIC.

    A share link is not a session. It is a grant naming a token. The browser keeps its tokens and sends them on every call in one header. The server rebuilds the principal list per request. Nothing is stored server-side, so there is no session to leak and no cookie to forge.

    every API call
    GET /api/method/drive.list?parent=q3
X-Drive-Links: kQ8vRt2mNp4wXz9bLc1AeF,7hJdY3sVn6QpTk0RmZuW2B.<ticket>
# bare token, or token.ticket once a password link is unlocked

    A password link never verifies the password twice. Unlocking returns an HMAC ticket bound to the token and the password hash, valid 30 days. Each later request costs one HMAC. Change the password or rotate the link and every ticket dies at once, because the input to the HMAC changed. No row is written anywhere.

    How the answer is composed

    Two passes, in order. The rule in one sentence: a deny on you is final, and a link can only raise you.

    What that means in practice

    SituationOutcome
    Priya has EDIT on Reports. She clicks a READ link to a file inside it. She keeps EDIT. A link never lowers anyone.
    Bob is denied on Reports. Someone sends him a link to a file inside it. Refused. A deny naming a person beats a link anywhere below it.
    Bob is an ordinary member with $GENERAL UPLOAD in the Shared Root, and gets an EDIT link. He edits. Links work for members, not only for guests.
    A guest opens a COMMENT link on a published document. The guest comments. This is how anonymous comments work now.
    One file inside a published folder is unpublished. The nearer $PUBLIC deny wins, and it cuts link holders of the folder too.

    Roots, and what happens when someone leaves

    A Drive Root is where a tree starts and where quota is counted. A business site has one Shared root plus one Personal root per person. A personal site has Personal roots only.

    Offboarding today would mean rewriting every node a leaver owns. In the new model it is one field on one row:

    the whole offboarding operation
    drive_root.state = "Archived"

    No node is written. No path is rewritten. No owner is rewritten. No chunked background job, no lock. Everyone the leaver shared with keeps their access, because access was never derived from ownership. Archived roots vanish from listings and appear in their own view.

    Owning a file grants nothing. This is the single change that makes offboarding cheap. Ownership becomes an accounting and audit fact. Rights come from grant rows, always.

    One contract for every product

    Drive is not another product beside Writer and Sheets. It is the layer they all sit on.

    Who owns what

    Drive owns
    • The title
    • The place in the tree
    • Grants and sharing
    • Lifecycle: trash, restore, purge, retention
    • Versions
    • Comments
    • Activity, recents, favourites
    • Previews
    The product owns
    • The live document body
    • Its change log, if it has one
    • Its collaboration state
    • Its editor
    • Its internal counters

    A content doctype loses its title field and its trashed field. There is no mirroring in either direction, because there is nothing to mirror: the node holds the only copy.

    What a product declares

    PartContents
    IdentityIts doctype, its mime type, the field that links back to the node.
    FactoriesCreate empty. Duplicate. Import from a file node.
    BytesExport to a format. Produce version bytes. Restore from version bytes.
    Cleanupon_purge. Drive never reaches into a product's tables.
    SatellitesIts own doctypes that take their rights from the node. Read to see, Edit to change. The product writes no permission code for them.
    Drive calls the product. The product calls Drive for four things only: check a permission, touch after an edit, take a version now, and create or copy a document here.

    What this removes

    ProductGoes away
    Sheets DocShare rows and three share endpoints. Its own trashed fields and a second 30-day purge clock. Sheet Snapshot becomes a Drive version; its retention ladder becomes the site-wide one.
    Writer Writer Version becomes a Drive version. Comments move out of the second Yjs blob into a Drive table, so the Comment role becomes enforceable.
    Slides The on_update hook that force-published every composite deck on every save. Media get nodes under the deck.
    Drive About 2,500 lines of storage plumbing: the backend abstraction, chunked upload, serving, thumbnail sidecars, trash-on-disk, quota. The framework does it.

    Previews, versions, and bytes

    Preview

    One 512 px WebP per node, in Drive Node Preview. The row records which blob it was rendered from, so uploading the same file twice renders once.

    A listing has already passed the permission check, so it mints a short-lived signed /f/ URL per tile. No per-tile permission request, no Python streaming.

    Version

    Drive Node Version holds versions of documents and of ordinary files. Replacing a file keeps the old bytes as a version. Immutable.

    One retention ladder for the whole site: keep everything for 24 hours, then hourly to 7 days, daily to 30 days, weekly to 90 days. Named and pinned versions stay until the node is purged.

    Exports are never stored. A Writer document downloaded as PDF, or a sheet as XLSX, is produced on request and streamed. Only the preview image is kept.

    Drive deletes no bytes

    Blobs are content-addressed and shared. Deleting a node drops a reference; the framework's garbage collector removes the bytes once nothing points at them. It finds the references from metadata: every Link field that points at File Blob. An app that adds one is covered on the next run without registering anything.

    the liveness test, one NOT EXISTS per reference column
    select b.name, b.key, b.driver, b.is_private
from `tabFile Blob` b
where b.modified < %(cutoff)s
  and not exists (select 1 from `tabFile` where blob = b.name)
  and not exists (select 1 from `tabDrive Node` where blob = b.name)
  and not exists (select 1 from `tabSingles`
                  where doctype = 'X' and field = 'y' and value = b.name)
limit %(batch)s

    If discovery fails, say an app is installed but not migrated, the run deletes nothing and logs an error. A blob kept one more day costs disk. A blob deleted under an incomplete reference set costs data.

    WebDAV rides the same engine

    Drive already speaks WebDAV, so Finder and Windows Explorer can mount it. The new engine does not get a special case: the DAV handlers call the same SDK, write the same activity rows, and read the same grants. What changes is that every method now names one role.

    MethodRoleChecked on
    PROPFINDREADthe target; children appear at READ and above
    GET, HEADREADthe node
    PUT (create)UPLOADthe parent folder
    PUT (replace)EDITthe node
    MKCOLUPLOADthe parent folder
    DELETEEDITthe node
    MOVEEDIT + UPLOADEDIT on the source, UPLOAD on the destination
    COPYREAD + UPLOADunreadable children are skipped
    PROPPATCHEDITthe node

    Three mounts appear at the top: Home, Everyone, and Shared with me. Documents show up as read-only export files. A sheet appears as Budget.xlsx and streams its export on GET, but refuses PUT. Something a user cannot read returns 404, never 403, so the tree never leaks names.

    What is still open

    Five decisions remain. Two of them block everything else.

    #QuestionWhat has to be settled
    010 Quota policy What counts against a root: trashed nodes, versions, previews, document bodies, in-flight reservations. Where usage is stored. Who pays for an archived root, and whether it is ever reclaimed.
    011 Migration mapping The source-to-target mapping is written, including the five-flag table. What is missing is the order, idempotency, and the rollback story.
    012 Slides media Where slide images sit as nodes, how paste-across-decks behaves under content addressing, and what a template is now that sharing has one home.
    014 HTTP API surface The endpoint list, request and response shapes, error codes, paging. Several endpoints are already pinned by earlier decisions.
    013 Write the spec The deliverable: frozen schemas and indexes, the engine's exact queries, the content SDK, the HTTP API, the WebDAV mapping, the framework asks, the migration. Blocked by all the rest.

    Deliberately out of scope

    Not in this effort
    • Frontend changes: share dialog, upload client, list views. Backend and HTTP API only.
    • Migrating standalone frappe/drive, which still has the Team model. Suite sites only.
    Ruled out, with a reason
    • Many shared spaces. It rebuilds the Team model that was already dissolved, and neither deployment needs it. A third kind is one Select option away if that changes.
    • Blind drop-box, upload without seeing the folder. UPLOAD contains READ in a strict ladder, so the state cannot be expressed.

    Known unknowns

    Every benchmark number on this page came from a single database connection. Behaviour under concurrent load has not been measured. Folder selectivity was measured without trashed rows mixed in. A derived index for search-within-shared may still be needed; the synthetic benchmark said the plain query is fine, and real data has not confirmed it.
