    Suite · Drive layer · Decision 012

    Slide images

    A slide holds pictures. Today Slides guards those pictures with its own code. This page shows how that works, why it breaks, and the first choice we have to make.

    Closed · 9 of 9 decided · Read from the code on 4 September 2026

    What a deck is made of

    Start with the pieces. A deck is one Presentation row. It owns a list of Slide rows. Each slide keeps its content in a single blob of JSON called elements: a text box here, a picture there, each with a position and a size.

    suite/slides/doctype/slide/slide.json:25 — one slide
    {
  "elements": [
    { "type": "text",  "left": 40, "top": 60, "content": "Q3 results" },
    { "type": "image", "left": 40, "top": 180,
      "src": "/private/files/logo.webp",     // the picture
      "attachmentName": "abc123" }              // a soft hint, nothing checks it
  ]
}

    The picture itself is not in that JSON. Only a path to it is. The bytes sit in a separate table that the Frappe framework calls File.

    One idea to hold on to. A slide points at a picture with a plain text path. Nothing ties the two together. No foreign key, no ownership. Delete the slide and the picture stays.

    Where a slide image lives today

    Faris uploads logo.webp into his deck. Three things happen.

    What Faris sees in Drive
    My Drive/
└── Q3 deck            (the deck)

    logo.webp is hidden. One line does it: drive/api/list.py:250 drops every row that has attached_to_doctype set.

    What the database holds
    My Drive/
├── Q3 deck            (the deck)
└── logo.webp          (hidden, no tie to the deck)

    The picture is a sibling of the deck, not a part of it. It belongs to whoever uploaded it.

    Why Slides needs its own guard

    Now Priya opens the deck. She may read the deck, so she must see the logo. But the logo is a private file in Faris's folder. Drive would say no.

    So Slides does not use the normal file URL. It sends every picture through its own endpoint, and that endpoint answers a different question: is this picture used by a deck you are allowed to read?

    suite/slides/api/file.py:110 — the media endpoint
    def get_media_file(src, presentation):
    # src         = /private/files/logo.webp
    # presentation = "the deck I claim to be looking at"

    The endpoint is 122 lines. Only 13 of them send the file. The rest decide who may have it, in four separate rules:

    #RuleWhy it exists
    1 Find every deck that has a File row for this path. Allow if you can read any of them. The same picture is copied into many decks.
    2 Also allow the decks that a composite deck pulls in. A composite deck shows other decks' slides, so it shows their pictures.
    3 If any deck holding this path is a template, allow it to everyone. Picking a template layout copies its pictures into your deck, but no File row follows.
    4 Unknown path → 404. Otherwise → 403. Do not leak which paths exist.

    The cost. Slides owns a second, private permission system. It knows nothing about sharing links, published decks, denied access, or trash. Every rule Drive gains has to be re-invented here, or the two drift apart.

    Three holes we already know about

    Templates

    A template deck is readable by everyone, in code, and it has no Drive row at all (presentation.py:496). Decision 005 says sharing has one home. This breaks it.

    Composites

    A composite deck used to be forced public. Decision 007 stopped that. Its pictures must now be checked against each borrowed deck, one by one.

    Nothing is cleaned up

    Delete a picture from a slide and the File row lives forever. Duplicate a deck ten times and you get ten more rows.

    What "make it a node" means

    In the new Drive layer, everything in the site is a node: a row with a path. A folder is a node. A file is a node. A deck is a node. One table answers "who may touch this", by walking the path.

    So the proposal is: stop making the picture a loose file in Faris's folder. Make it a node inside the deck. Then the deck's own permissions cover it, and Slides needs no guard.

    Today
    My Drive/
├── Q3 deck
└── logo.webp   ← guarded by
                  slides/api/file.py
    Proposed
    My Drive/
└── Q3 deck/
    └── logo.webp   ← guarded by
                      the deck above it

    Writer already works this way. A Writer document's Drive row is a folder. Images pasted into the document are uploaded as children of it (writer/api/embed.py:12), and one small endpoint serves them after checking read on the parent. Nine lines, not 122.

    suite/writer/api/embed.py — the whole thing
    def add(file_id):
    embed = upload_file(parent=file_id, embed=1)   # child of the document

def get(id):
    parent = <the document this embed hangs under>
    if not user_has_permission(parent, "read"):
        raise PermissionError            # one check, no special cases

    Question 1 — where does the picture sit?

    Four places it could go. The rest of the decisions (copy and paste, the URL in the JSON, templates, cleanup) all hang off this one.

    Option A · recommended

    A child of the deck

    My Drive/
└── Q3 deck/
    ├── logo.webp
    └── intro.mp4

    Good: the deck's permissions cover the picture with no extra code. Share the deck, the pictures follow. Deny the deck, they stop. Trash the deck, they go with it. The 122-line endpoint is deleted.

    Cost: a deck node now has children. Listings must refuse to open a deck like a folder.

    Option B

    A child of a hidden folder inside the deck

    My Drive/
└── Q3 deck/
    └── .media/
        ├── logo.webp
        └── intro.mp4

    Good: same permissions as A. The deck's child list stays clean without a listing rule.

    Cost: one more level to walk, a reserved name to defend, and a folder the user can stumble into. Writer creates a .embeds folder like this today and then does not use it for permissions.

    Option C

    Not a node — a side table

    Drive Node Attachment
  node      = "Q3 deck"
  blob      = <the bytes>
  filename  = "logo.webp"

    Good: invisible everywhere. No path, no listing rule, no reserved name.

    Cost: three decisions already made stop applying. Decision 006 puts picture thumbnails on nodes. Decision 010 charges storage per node. Garbage collection counts node references. A side table needs all three written again.

    Option D

    Leave it in the uploader's folder, add a share

    My Drive/
├── Q3 deck
└── logo.webp   + a grant for every deck viewer

    Cost: this is today's layout with grants bolted on. Every share of the deck now has to fan out to each picture, and every unshare has to undo it. It is the bug we are leaving, written in a new table.

    Decided · 4 September 2026

    A. The picture is a child node of the deck

    The path walk that answers "can Priya read this deck" also answers "can Priya read the logo inside it". The 122-line endpoint goes.

    And a deck is always a leaf. Drive is the only list view in Suite — for documents, sheets and decks alike — and clicking any of them opens its editor. No listing descends into a content document, so media nodes are never shown. That is one rule for all three apps, not a Slides special case.

    Question 2 — what does the slide point at?

    The picture is now a node under the deck. But the slide JSON still holds a piece of text in src. What text?

    This matters more than it looks, because the same bytes are shared. The framework stores a file once per content hash. Upload the same logo to ten decks and you get ten rows and one copy of the bytes.

    The three things src could hold

    Option A

    The node

    "src": "/drive/media/n_8f21c4"

    Good: one permission check, on the node, exactly like every other Drive read.

    Cost: every request for bytes goes through Python. Video needs byte ranges, so we keep writing a streamer. And the browser caches the same logo three times, once per deck, because the URL differs.

    Option B

    The bytes

    "src": "/f/ab3f9c…/logo.webp"

    Good: copy and paste rewrites nothing. One cache entry for one picture.

    Cost: the bytes do not know who owns them. To check permission the server must search for a node that holds this blob and that you may read. That is rule 1 of today's endpoint, rebuilt.

    Option C · recommended

    The node in the slide, the bytes on the wire

    slide JSON   "src": "n_8f21c4"          ← the node

on open      Drive checks the deck once, then hands back
             "/f/ab3f9c…/logo.webp?sig=…&exp=…"   ← a signed link

browser      fetches that link directly. No Python.

    Good: one permission check per deck open, not one per picture. Byte ranges, caching and resume come from the file server for free, so the streamer is deleted outright. The browser caches by blob, so one logo is one cache entry across every deck.

    This is already the pattern. Decision 006 serves every Drive thumbnail exactly this way: check the folder once, mint short-lived signed links, let the browser fetch them.

    Decided · 4 September 2026

    C. The node in the slide, a signed blob link on the wire

    Drive checks the deck once when it opens and hands back short-lived signed /f/ links. The browser fetches them directly. No Python in the byte path, so the whole 122-line endpoint goes, streamer included.

    Question 3 — the link expires. Then what?

    A signed link carries an expiry time. That is what makes it safe to hand out. It is also the one loose end in decision 2, and Slides has two cases that outlive a short link.

    Case 1 · the long meeting

    Someone opens a deck at 9 a.m. and presents from it at 4 p.m. without reloading the page. Every picture link minted at 9 a.m. is dead.

    Case 2 · the plane

    Slides can pin a deck for offline use. A service worker stores the pictures in a cache and serves them with no network at all (stores/offlineCopy.js).

    Three ways to handle case 1

    Option A

    Make the link live a long time

    exp = now + 24 hours

    Good: nothing to build.

    Cost: unshare a deck at noon and the pictures stay reachable until tomorrow. Drive already accepts a short window for this. A day is a different promise.

    Option B · recommended

    Short link, the page asks again

    deck opens   →  links, each good for a short window
near expiry  →  the page calls the same endpoint again
                and swaps in fresh links

    Good: one extra call on a timer, reusing the call the deck already makes. Revoking access bites within the window. The window is a Drive-wide setting shared with thumbnails, not a Slides number.

    Cost: the editor keeps a timer. About twenty lines.

    Option C

    A permanent address that redirects

    "src": "/drive/media/n_8f21c4"

  →  Drive checks permission, answers 302
  →  browser follows to a fresh signed /f/ link

    Good: the address in the slide never goes stale. No timer. This is the shape decision 009 chose for WebDAV downloads.

    Cost: a permission check per picture, not per deck. A deck with forty images costs forty round trips on open — the per-picture cost we are removing.

    Decided · 4 September 2026

    B. Short link, the page asks again on a timer

    The window is a Drive-wide setting shared with thumbnails. Slides does not pick a number.

    And offline is stated, not implied: pinning a deck keeps its pictures until you unpin it. Unsharing does not reach into a laptop. The same promise as downloading a file.

    A bonus that falls out

    Today the owner and a viewer fetch the same picture under two different URLs, so Slides carries canonicalMediaKey.ts to make one cache entry serve both. Now everyone fetches /f/<blob>. Strip the signature and the cache key is the blob itself. That file goes, and one logo is one cache entry across every pinned deck.

    Question 4 — copy and paste

    Faris copies a slide out of the Q3 deck and pastes it into the Q4 deck. The slide carries a logo. The logo is a node under the Q3 deck, and the Q4 deck cannot borrow it: a viewer of Q4 may have no rights at all on Q3.

    Three places this happens today, all through one function (presentation.py:444):

    • paste one picture into another deck
    • paste a whole slide into another deck
    • duplicate a whole deck

    What paste should do

    Option A · recommended

    Copy the node, share the bytes

    Q3 deck/
└── logo.webp   node n_8f21  ─┐
                              ├─>  one blob  ab3f9c…
Q4 deck/                      │
└── logo.webp   node n_c40a  ─┘   new node, no new bytes

the pasted slide's "src" is rewritten  n_8f21 → n_c40a

    Good: the Q4 deck owns everything it shows. Share it, delete the Q3 deck, archive Faris — the Q4 deck is unaffected. No bytes are copied; the blob is shared. This is the copy that decision 014 already defines: a new node owned by whoever pasted, no grants and no history carried over.

    Check on paste: you must be able to read the source node. Same guard as today.

    Option B

    Point at the original

    Q4 deck's slide  "src": n_8f21   ← still the Q3 deck's node

    Cost: anyone who opens Q4 now needs read on Q3. Delete the Q3 deck and the Q4 deck loses its picture. This is the coupling we are removing.

    The price of A, stated plainly. Decision 010 charges storage per node, not per blob. A 50 MB video pasted into three decks is 150 MB of quota against one 50 MB blob on disk. That is deliberate — a deck you can delete on your own must cost you something — but you should agree to it here rather than find it later.

    A smaller question inside it

    Paste the same logo twice into the same deck. One node reused, or two nodes with identical bytes?

    Reuse · recommended

    One node per deck per blob. Both slides point at it. Charged once. A repeated header image costs what it looks like it costs.

    Always a new node

    Simpler to write, and each picture can be renamed on its own. But a logo on twenty slides is twenty nodes and twenty charges.

    Decided · 4 September 2026

    A. Copy the node across decks, reuse it inside one

    The blob is shared either way. What is decided is who is on the hook: the destination deck owns and pays for what it shows. One node per deck per blob, so a logo on twenty slides is one node and one charge.

    Question 5 — when does a picture die?

    Two halves. One is free, one is not.

    Free · falls out of decision 1

    The deck goes, its pictures go

    trash the deck    →  Q3 deck/ and everything under it is trashed
restore it        →  they come back
purge it          →  they are purged, the blob follows if nobody else names it

    Nothing to build. The pictures are inside the deck, so they move with it. Today the picture sits in the uploader's folder and survives the deck forever.

    Not free

    The picture is removed but the deck lives

    Faris deletes the logo from slide 3 and keeps working. Nothing tells Drive. The slide's content is one opaque blob of JSON, so Drive cannot see that the picture is no longer named. Today the file simply stays, forever. Now it also costs quota.

    Three ways to handle it

    Option A

    Never delete

    Good: nothing to build. Undo always works.

    Cost: a deck worked on for a year carries every picture ever dropped into it, and charges for all of them. This is today's behaviour with a bill attached.

    Option B · recommended

    Ask the app, on a timer

    each night, for each deck touched since the last run:
    ask Slides   "which pictures do you still use?"
    any node under the deck not in that answer,
    and older than a grace period   →  trash it

    Good: Slides is the only thing that can read its own JSON, so Slides answers. Drive does the deleting. Undo and collaboration are safe because nothing is removed the moment it stops being used.

    Worth noting: this is not a Slides feature. Writer has the same hole with pasted images. It should be a new line in the contract every content app signs (decision 005) — "list the nodes you still use" — and then Writer gets the cleanup for free.

    Option C

    Delete the moment the element goes

    Good: immediate. No sweep.

    Cost: undo loses the picture. Two people editing at once means "removed" is not a fact yet. Every removal becomes a write.

    Decided · 4 September 2026

    B. Drive sweeps. The app answers one question.

    Drive owns everything except one line

Drive   picks the decks to check, keeps the grace period,
        does the trashing, runs the job          ← written once

Slides  "which nodes do I still use?"            ← five lines
Writer  "which nodes do I still use?"            ← five lines
Sheets  "which nodes do I still use?"            ← five lines

    No app writes sweep code. The app cannot avoid answering the question, because only it can read its own content, but that is one function, not a job. It becomes a new line in the contract every content app signs (decision 005), so Writer's pasted images get cleaned up for free.

    Trashed, not purged. An unused picture lands in the deck owner's bin and follows the normal 30-day clock. Nothing in this map deletes a person's content without showing it to them first.

    Question 6 — what is a template?

    This is not a Slides question. Two apps already ship templates, and both solve them by writing a permission in code.

    AppShapeWho may read one
    Slides a flag on the deck itself, is_template everyone, decided in an if
    presentation.py:496
    Writer a separate Writer Template doctype everyone signed in, decided in an if
    writer/overrides/__init__.py:16
    Sheets none yet —

    Two apps, two different shapes, the same hole. Fix it in Slides only and Sheets will invent a third shape next year. Decision 005 says sharing has one home; this is the last place in Suite that ignores it.

    Strip it back: what is a template, really?

    Only two things ever happen to one.

    list     "show me the ones I can start from"
create   "make me a new document from this one"

    Drive already does both. Listing readable things is what Drive is. And "make a new document from this one" is copy — the primitive decision 014 already defines, and the same one decision 4 above uses for paste.

    The abstraction · recommended

    A template is a document you may read, marked as a starting point

    Drive Node
  ...
  is_template   ← one flag, on the node, for every app
    OperationWhat it becomes
    Who may use a templatethe grant on its node. Nothing else.
    List templatesone Drive query: nodes I can read, flagged, of this content type
    New from templatecopy — already built
    Ship "Light" and "Dark"decks in Administrator's drive, granted Read to everyone signed in
    A company's own templatemark a document, share it. No code.
    Sheets templates one daynothing to build

    What this deletes: both if bypasses, the Writer Template doctype and its two permission functions, Slides' is_template branch and its is_template_media rule, and the "a template has no Drive row" special case.

    Decided · 4 September 2026

    A template is a document you may read, marked as a starting point

    is_template is one flag on Drive Node. Permission is the grant on that node and nothing else. Listing is one Drive query. Starting from one is copy.

    Two rules with it: templates are hidden from ordinary listings and appear only in the template picker; shipped templates are granted to everyone signed in, not to the public.

    Hand off: this changes Writer as much as Slides. It goes to the content app contract and to the spec, not into a Slides patch.

    Question 7 — composite decks

    A composite deck shows other decks' slides inside itself. It holds a list of references, and when you open it, those decks' slides are pulled in live (presentation.py:559). Change the source deck and the composite changes with it.

    Today this only works because composites are forced public. Saving one writes a "everyone may read" row on the composite (presentation.py:47), and every referenced deck must already be public. Decision 007 stopped forcing that. So the rule has to be rewritten.

    Whose permission covers a borrowed picture?

    Settled by decision 007 · confirming

    The deck it came from. Never the composite.

    open the All-hands deck
  can I read Sales deck?     yes  →  inline its slides, mint links for its pictures
  can I read Product deck?   no   →  do not inline, mint nothing

    One check per referenced deck, for the person looking. Being named by a composite grants nothing. Nothing is copied — the composite stays live.

    Decided · 4 September 2026

    Reference anything you can read

    The save-time check becomes the ordinary one: can you read the deck you point at. A composite is a view, so its contents differ by who is looking. The forced-public row and the public-reference rule both go.

    And the API stops dropping. Today an unreadable reference vanishes silently (presentation.py:571) and the slide count changes mid-presentation. It is returned marked "you cannot read this"; the client chooses whether to draw a placeholder.

    Question 8 — the deck's own picture

    Every deck shows a small picture of its first slide in a list. Slides makes it in an unusual way, and the way it is made constrains us.

    how a deck thumbnail is made today
    the browser draws the slide, screenshots the page itself,
sends a webp back to the server                      useThumbnailCapture.js:89

the server stores it as a File on the deck           presentation.py:159
and writes the field without touching "modified"   presentation.py:184

    That last line is not an accident. If saving the picture bumps the deck's modified time, the open editor believes someone else edited the deck and throws away unsynced local changes. A comment in the code says so.

    Decision 006 already chose the mechanism: Drive keeps one small picture per node in Drive Node Preview, it never renders a document itself, and the app pushes a ready image through one Drive call. Slides keeps its browser capture. So the field on the deck goes and the row on the node replaces it. Two details are left.

    Decided · 4 September 2026

    The preview row replaces the field. No touch, and duplicates carry it.

    Pushing a preview is not an edit: it writes the preview row and nothing else. Otherwise "sorted by last modified" reorders decks because someone looked at one, and the open editor drops unsynced work.

    A duplicated deck copies the preview row and points at the same bytes, so it looks right the instant it appears. Accepted consequence: a deck made by script or by migration has a blank tile until a person opens it.

    Question 9 — the upload itself

    One last path. Slides does not keep what you upload. It converts every image to webp, and it does so after the file is already stored.

    presentation.py:590 — today
    1. store the file the user picked            logo.png
2. convert it to webp on disk, by rewriting the path string
3. delete the original File row              presentation.py:611

    This cannot be ported as it stands. Under the new model bytes never change: replacing a node's bytes keeps the old ones as a version (decision 006), and versions cost quota (decision 010). Port this literally and every image upload leaves a dead copy of itself behind, charged to the uploader.

    When to convert

    Option A · recommended

    Convert first, then make the node

    bytes arrive  →  Slides converts to webp  →  Drive creates the node

one node, one blob, no version, nothing to delete

    Good: the node is born as the picture it will always be. No replace, no version, no cleanup step, no stale reference in the slide JSON.

    Where the conversion lives: in Slides, before it calls Drive. Drive must not convert what people upload — someone who puts a PNG in their drive expects a PNG back. This is a Slides policy, so it stays in Slides, and no new Drive concept is needed.

    Option B

    Create the node, then replace its bytes

    The literal port. Every upload creates a version holding the original, charged to the uploader, that nobody asked for.

    Option C

    Convert in the browser

    Cheapest for the server, and the original never leaves the machine. But nothing on the server guarantees the result, so the rule is not enforced — and video and other types still need the server anyway.

    Decided · 4 September 2026

    A. Convert first, then make the node

    The node is born as the picture it will always be. The conversion stays in Slides, before the Drive call, because Drive must not convert what people upload.

    Two things that follow, not decisions

    Media tiles come free

    A media node is an ordinary file node with a picture mime, so Drive renders it a preview like any other. The media picker gets thumbnails with no Slides code. This is the handoff decision 006 made to this ticket.

    Uploads can now run out of room

    Decision 010 makes the browser declare a size before uploading and returns a distinct out-of-space error. Slide media uploads use the same call, so they get the same error — not a permission failure.
